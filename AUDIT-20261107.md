Persistence is one unversioned `todos` array plus `reminderEnabled`, `reminderTime`,
`snoozeMinutes`, `reminderHistory`, `appTitle`, `quoteSettings`, `todoViewMode`,
`lang`, and exam migration flags. Todo IDs are normally UUIDs (timestamp/random
fallback); data also contains deterministic imported IDs. Dates are `YYYY-MM-DD`
calendar strings, completion/snooze times are epoch milliseconds, and `createdAt`
is an ISO timestamp. There is no schema validation, transaction, or single writer.

## Correctness and reliability findings

### F1 — High: whole-array writes can lose unrelated user changes

`popup.js:1041–1057` saves its entire in-memory array. Worker reset, snooze,
snooze-clear and completion handlers independently read/modify/write the same key
(`background.js:33–62`, `232–274`). For example, a worker read of tasks A/B can
precede popup creation of C; its later write completing A replaces storage with
A/B and deletes C. The reverse interleaving can undo notification completion.
`pendingSelfWriteTokens` (`popup.js:57–59`, `82–96`) only suppresses render echoes;
it is not concurrency control. Worker callbacks can also overlap one another.

Recommendation: route todo mutations through one serialized worker-owned store,
apply operations by ID against fresh state, and acknowledge committed revisions.
Locking only writes or adding another read before saving does not solve this.
This requires a coordinated persistence protocol change; see remaining risks.

### F2 — High: a stale completion timer can delete a reopened task

`scheduleFadeTimer()` captures the original todo object (`popup.js:873–900`).
`syncTodosFromStorage()` replaces the array and `scheduleAllFadeTimers()` only
rearms completed items (`806–819`, `918–925`); it never cancels timers for items
that are now active or missing. An old timer therefore still deletes by ID after
a background/storage update reopens the task. The second 500ms deletion timer is
not tracked at all, so unchecking during the fade animation also fails to cancel
the deletion. This is irreversible task loss within normal UI interactions.

### F3 — High: UTC parsing breaks local deadlines and repeat advancement

`formatDateDisplay()` (`todo-core.js:35–41`), `isTodoOverdue()` (`222–228`),
`advanceRepeatDate()` (`279–290`) and `advanceDueDateToFuture()` (`306–317`) feed
date-only strings to `new Date()`, which interprets them as UTC, then read local
components. Verified under `TZ=America/Los_Angeles`:

- `formatDateDisplay('2026-06-05')` returns `06/04`.
- A June 1 task is already overdue at local noon on June 1.
- Advancing `2026-06-01` daily returns `2026-06-01`; weekly returns June 7.

The daily no-op also prevents rollover from advancing a stale deadline. Separately,
the 1,000-iteration guard leaves deadlines over 1,000 daily periods stale even in
UTC. Use a validated local calendar parser consistently; preserve month clamping.

### F4 — High: snooze state and alarm state diverge

`reschedule()` only removes `todo_`/`reset_` alarms (`background.js:116–155`). It
neither restores a persisted future `snoozedUntil` nor removes a snooze after edit,
completion via popup, deletion, or disabling reminders. `updateTodo()` clears
`snoozedUntil` (`popup.js:831–834`) but the old alarm can still notify at the old
time. A daily alarm explicitly clears a pending snooze (`background.js:67`),
ignoring the user's chosen future time. Re-enabling reminders after disabling
can consequently deliver a stale alarm.

Reconcile all managed alarms with current todos/settings, restore valid future
snoozes, discard obsolete alarms, and check live snooze state before delivery.

### F5 — Medium: Re-remind stops after one follow-up

`background.js:72–77` creates the next nag only for a `todo_` alarm. The follow-up
is named `snooze_`; its handler never rearms the interval. It also does not persist
the scheduled nag timestamp. This disagrees with the documented repeated interval
behavior (`README.md:140`, `239`) while an unfinished task remains open. Rearm
after each delivery and persist the next timestamp for schedule reconciliation.

### F6 — Medium: daily reminders drift across daylight saving changes

`background.js:285–287` claims a 1,440-minute interval preserves clock time. It
preserves elapsed time instead: local 09:30 becomes 10:30 or 08:30 across DST.
Schedule the next local calendar occurrence after each daily delivery instead.

### F7 — Medium: editing a snoozed task changes its permanent reminder

`showEditForm()` populates the reminder field with `todoVisibleReminderTime()`
(`popup.js:127–137`, `749`), which returns the temporary snooze clock time.
`updateTodo()` saves that as the regular `reminderTime` (`831–833`), even if the
user only changed the task title. Show/edit the permanent reminder field directly.

### F8 — Medium: quote entities are corrupted by number styling

`renderTextWithSystemNumbers()` (`todo-core.js:404–415`) escapes text first, then
wraps all digits in spans, including digits inside HTML entities. Verified:
`don't 123` becomes `don&#<span class="num">39</span>;t ...`. Split/style the
original numeric runs and escape each piece, preserving literal punctuation and
the existing protection against user HTML.

### F9 — Medium: completion timestamp migration is not persisted

`loadTodos()` stamps legacy completed todos missing `completedAt`
(`popup.js:1086–1091`) but that change is absent from the save conditions
(`1101–1105`). When the other migrations have already run, reopening the popup
restarts the one-minute expiry window; a legacy repeat can lack a persisted reset
timestamp indefinitely. Track and save this migration with the others.

### F10 — Medium: overlapping reschedules can restore an obsolete schedule

`reschedule()` performs an async storage read and alarm enumeration without
serialization (`background.js:109–157`). Multiple update messages/startup/reset
callbacks can interleave, allowing older work to clear and recreate alarms after
newer work. Alarm clears are also not awaited before recreating the same names.
Serialize scheduler runs and complete clears before building their replacements.

### F11 — Lower-priority residual behavior and robustness gaps

- `popup.js:789` gives parsed dates priority over an explicitly selected deadline,
  unlike explicit reminder/repeat fields. English prefix matching
  (`todo-core.js:126–172`) consumes words such as `todayland` and `weeklyreport`.
  Neither path has an explicit product rule/test defining ambiguous input.
- Todo IDs are interpolated unescaped in HTML attributes/selectors
  (`popup.js:732`, `880`, `973–984`). Generated UUIDs/import IDs are safe; arbitrary
  legacy/corrupt IDs containing quotes can break markup or throw selector errors.
  `renderReminderHistory()` also uses a text-node escape helper inside an
  attribute (`158–160`, `1035–1039`), which does not escape quotes.
- No schema check protects popup loading from non-array `todos` or null entries
  (`popup.js:1063`, `1087`); several worker loops similarly assume object entries.
  Storage failures are mostly logged or ignored; `notifyTodo()` does not handle
  notification creation errors (`background.js:181–183`), and its dedupe timestamp
  is recorded before creation succeeds (`187–193`). Dedupe disappears when the
  service worker restarts, and its map never evicts old IDs during a worker run.
- External storage synchronization reconstructs the inline editor and discards
  unsaved input (`popup.js:806–818`). Changing another task's notification while
  editing can therefore reset the draft. Full list rendering can detach the moved
  edit form (`950–988`) until an explicit hide/show reinserts it.
- Custom selects hide their native controls with `display:none` and use clickable
  divs without keyboard semantics (`styles.css:400–402`, `popup.html:89–103`,
  `114–130`, `popup.js:619–660`). Checkbox keyboard support does not cover these.
  IME protection exists for add/reminder inputs, but not edit-title keypress,
  app-title or quote Enter handlers (`popup.js:461`, `497`, `517–522`).
- One-shot validation accepts normalized impossible dates such as February 31
  (`background.js:291–307`); removing a one-shot deadline falls back to daily
  scheduling (`277–288`). These validation/fallback bugs were fixed in this audit.
  The UI still exposes no control for `oneShotReminder`.
- The screenshot CDP client has no close/error rejection for pending commands,
  navigation timeout, or `Runtime.evaluate` exception check
  (`scripts/readme-screenshots.mjs:258–330`); a rendering error can hang generation
  or produce a misleading screenshot. Notification screenshots are HTML mockups,
  not OS notification integration coverage.

**Remaining highest priority: F1.** Snapshot-based persistence is still vulnerable
to lost updates between popup and worker writes. Scheduler serialization does not
make storage mutations transactional. Replacing every writer with a single
operation queue and a popup acknowledgement/rebase protocol is a broader change
than these independently verified lifecycle repairs; a partial lock/read-before-
write patch would leave the demonstrated race open. Address that protocol next.

handling limitations remain. This audit does not claim complete reliability or
end-to-end Chrome/OS coverage.
